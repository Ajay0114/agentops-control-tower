# AgentOps Telemetry Event Contract

**Contract version:** 1.0.0  
**Status:** Initial design  
**Purpose:** Standardized telemetry format for all AgentOps integrations.

## 1. Objective

Define a framework-independent event format that allows AgentOps to receive, validate, correlate and store telemetry from different AI agent platforms.

The same contract will be used by:
- Custom Python agents
- LangGraph integrations
- Kore.ai XO integrations
- Kore.ai Artemis integrations
- Future agent frameworks and external applications

## 2. Event Structure

Every telemetry event follows this structure:

| Section | Required | Description |
|---|---|---|
| schema_version | Yes | Version of the telemetry contract |
| event_id | Yes | Unique event identifier (UUID) |
| event_type | Yes | Type of event |
| occurred_at | Yes | UTC event timestamp |
| source | Yes | Originating platform and service |
| agent | Yes | Registered agent and version |
| context | Yes | Session, execution and tracing identifiers |
| operation | Yes | Operation details and execution status |
| model_usage | No | LLM model and token usage |
| error | No | Structured error information |
| payload | No | Input/output capture references and privacy mode |
| attributes | No | Additional event metadata |

## 3. Event Categories

### Agent lifecycle
- agent.execution.started
- agent.execution.completed
- agent.execution.failed

### LLM operations
- llm.request.started
- llm.request.completed
- llm.request.failed

### Tool operations
- tool.call.started
- tool.call.completed
- tool.call.failed

### Workflow operations
- workflow.started
- workflow.completed
- workflow.failed

### Agent state and context
- agent.state.changed
- agent.context.updated

## 4. Field Definitions

### 4.1 Event Metadata

- schema_version: String, currently 1.0.0.
- event_id: UUID generated by the producer.
- event_type: One of the supported event types.
- occurred_at: Time when the event occurred, expressed in UTC.

### 4.2 Source

- platform: Originating framework or runtime, such as custom-python, langgraph, kore-xo or kore-artemis.
- service_name: Application or service producing the event.
- environment: Environment in which the agent operates, such as development, staging or production.

### 4.3 Agent

- id: Registered AgentOps agent UUID.
- version_id: Optional registered agent-version UUID.
- version: Agent version label, such as 1.0.0.

### 4.4 Execution Context

- session_id: AgentOps session UUID.
- execution_id: AgentOps execution UUID.
- workflow_id: Optional external workflow identifier.
- trace_id: OpenTelemetry-compatible 32-character hexadecimal trace ID.
- span_id: OpenTelemetry-compatible 16-character hexadecimal span ID.
- parent_span_id: Optional parent span identifier.

### 4.5 Operation

- name: Operation name, such as product_lookup or customer_support.
- kind: agent, llm, tool, workflow or state.
- status: started, completed, failed or cancelled.
- duration_ms: Optional operation duration in milliseconds.

### 4.6 Model Usage

Optional information for LLM operations:

- provider: Model provider, such as OpenRouter or Azure OpenAI.
- model: Model identifier.
- input_tokens: Number of input tokens.
- output_tokens: Number of output tokens.
- total_tokens: Total tokens consumed.
- cost_usd: Optional estimated cost in USD.

### 4.7 Error

- type: Error class or category.
- code: Application-specific error code.
- message: Sanitized error description.
- retryable: Whether the operation may be retried.

Error information should be included when an operation fails.

### 4.8 Payload and Privacy

- capture_mode: metadata_only, redacted or restricted.
- input_ref: Optional reference to a stored input artifact.
- output_ref: Optional reference to a stored output artifact.
- redacted: Indicates whether sensitive content has been redacted.

Production defaults to metadata_only. Restricted payloads require explicit authorization and appropriate encryption and access controls.

### 4.9 Attributes

A flexible JSON object for additional metadata, such as:
- HTTP response status
- Retry attempt
- Tool-specific configuration
- Framework-specific execution metadata

Attributes must not be used to replace standard contract fields.

## 6. Validation Rules

1. Every event must have a valid UUID event_id.
2. schema_version must identify a supported contract version.
3. event_type must belong to the supported event taxonomy.
4. occurred_at must include timezone information and be normalized to UTC.
5. Agent, session and execution identifiers must reference valid records within the authenticated tenant.
6. Agent version must belong to the specified agent.
7. trace_id and span_id must follow OpenTelemetry identifier formats.
8. duration_ms cannot be negative.
9. Token counts cannot be negative.
10. Failed operations should include structured error information.
11. Model usage is optional for operations that do not invoke an LLM.
12. Unknown optional attributes may be retained without changing the standard contract.
13. Duplicate event IDs within the same tenant must not create duplicate records.
14. tenant_id must be derived from authenticated credentials, not accepted from an untrusted event body.

## 7. Event Processing Principles

- Validate incoming events before persistence.
- Associate events with the correct agent, session and execution.
- Preserve event timestamps from the originating system.
- Record ingestion timestamps separately.
- Support duplicate delivery safely.
- Avoid exposing sensitive payloads in ordinary logs.
- Keep ingestion resilient so telemetry failures do not crash the originating agent.

## 8. Future Extensions

The contract is designed to support future additions such as:

- Evaluation events
- Policy violation events
- Human approval events
- Incident creation events
- Agent dependency events
- Cost and performance events

These can be introduced through future compatible schema versions.
